# SingStreamBench: бенчмарк потоковых guardrail-моделей

Языковая модель отдаёт ответ по частям, и пользователь читает текст ещё до того, как
ответ дописан. Защитная модель (guard) читает тот же поток и должна остановить выдачу
раньше, чем опасный фрагмент попадёт на экран. Проверять поток можно после каждого
токена, после каждых восьми или только в самом конце: чем реже проверка, тем она дешевле
и тем больше текста успевает уйти пользователю.

Этот репозиторий измеряет такой компромисс на размеченных данных. Сейчас проверяется
[Qwen3Guard-Stream-0.6B](https://huggingface.co/Qwen/Qwen3Guard-Stream-0.6B), но код
рассчитан на подключение других guard-моделей.

## С чего начать 

Готовые результаты и графики лежат в двух ноутбуках, запускать модель для их просмотра
не нужно:

- [`notebooks/01_singstreambench_eda.ipynb`](notebooks/01_singstreambench_eda.ipynb) —
  что за датасет, откуда он и почему ему можно доверять;
- [`notebooks/02_streaming_benchmark.ipynb`](notebooks/02_streaming_benchmark.ipynb) —
  метрики и графики по сохранённому прогону guard-модели.

Ноутбуки сохранены вместе с выводами, поэтому таблицы и графики видны сразу при
открытии файла.

## Данные

Источник — [inclusionAI/SingStreamBench](https://huggingface.co/datasets/inclusionAI/SingStreamBench). Это 210 вручную проверенных англоязычных примеров. Каждый пример
содержит запрос, полный ответ модели, две метки безопасности и точную позицию символа, с
которого ответ становится опасным.

Ревизия датасета закреплена в [`configs/qwen3guard_baseline.yaml`](configs/qwen3guard_baseline.yaml),
а подготовленные поля описаны в [`docs/data_contract.md`](docs/data_contract.md). Текст
не нормализуется: guard видит ровно тот ответ, который размечали авторы датасета.

Датасет содержит чувствительные запросы и ответы. Он предназначен для исследований
безопасности, а полные тексты не следует копировать в issues, логи и скриншоты.

## Словарь

| Термин | Значение |
|---|---|
| трасса | один пример датасета: запрос, ответ и разметка к ним |
| onset | позиция, с которой ответ становится опасным; в токенах это `unsafe_start_token` |
| режим буфера | как часто guard проверяет поток: каждый токен, каждые 8/16/32 токена, каждое предложение или один раз в конце |
| сигнал | первый токен, на котором guard сказал «опасно» |
| вмешательство | конец окна проверки, внутри которого нашёлся этот токен; раньше него остановить поток нельзя |
| leakage | сколько опасных токенов пользователь успел увидеть до остановки |
| политика | какие метки guard считает блокирующими: `strict` — `controversial` и `unsafe`, `conservative` — только `unsafe` |

## Что измеряется

Запрос и ответ оцениваются отдельно. Опасный запрос фиксируется как отдельный
результат, но не прекращает обработку ответа: иначе модерация запроса маскировала бы
качество модерации самого ответа. В датасете много опасных запросов с безопасными
ответами, то есть с корректными отказами, и их важно не блокировать.

Одна и та же последовательность решений guard переигрывается в шести режимах буфера:
`token`, `chunk_8`, `chunk_16`, `chunk_32`, `sentence` и `full_buffered`. Модель при этом
запускается один раз, поэтому режимы сравниваются на идентичных решениях.

Отчёт разделяет две группы чисел.

Качество классификации: доли ложных срабатываний и пропусков отдельно для запроса и для
ответа, по одной строке на политику. Эти числа не зависят от режима буфера.

Поведение в потоке: сколько опасных токенов утекло (среднее, медиана, p90), как часто
guard блокировал ответ до onset, на сколько токенов он опередил или опоздал, как часто
не сработал вовсе, сколько токенов пролежало в буфере между сигналом и остановкой,
сколько проверок это стоило и сколько заняло времени.

Доли сопровождаются 95% доверительным интервалом Уилсона, средние и квантили —
bootstrap-интервалом с фиксированным seed, а режимы сравниваются парным bootstrap
разности на одних и тех же трассах. Без интервалов разницу между двумя режимами на 210
примерах легко принять за результат, когда это случайность выборки.

## Установка

Нужны Python 3.11 и [uv](https://docs.astral.sh/uv/). Все команды запускаются из корня
репозитория, во встроенном терминале VS Code (меню Terminal → New Terminal) или в любом
другом.

```bash
uv sync --extra analysis --extra dev
```

Команда создаёт окружение `.venv` со всем, что нужно для чтения ноутбуков и запуска
тестов. Веса guard-модели на этом шаге не скачиваются.

Проверить, что окружение собрано правильно, можно теми же командами, что выполняет CI:

```bash
uv run pytest
uv run ruff check .
```

## Подготовка данных и модели

Этот шаг нужен только для запуска guard-модели, для чтения готовых ноутбуков он не
требуется.

```bash
uv sync --extra analysis --extra dev --extra models
uv run python scripts/prepare_singstreambench.py
uv run python scripts/validate_singstreambench.py
```

Скрипты скачивают датасет, сохраняют его в Parquet, пишут manifest с ревизией, checksum
и статистикой, а затем проверяют контракт данных. 

## Запуск прогонов

Профиль `smoke2` это проверка работоспособности кода:

```bash
uv run python scripts/run_qwen3guard.py --profile smoke2
uv run python scripts/build_reports.py --profile smoke2
```

Профиль `full` проходит все 210 трасс и даёт числа, которые можно обсуждать как
результат.

```bash
uv run python scripts/run_qwen3guard.py --profile full
uv run python scripts/build_reports.py --profile full
```

Тот же прогон запускается прямо из ноутбука `02_streaming_benchmark.ipynb`: в разделе
«Прогон Qwen3Guard» достаточно выбрать профиль и выполнить ячейку. Оба пути вызывают одну
функцию `run_or_load` из `src/streamguard_bench/pipeline.py`, читают один конфиг и пишут
в одни и те же файлы, поэтому результаты не зависят от способа запуска.

Повторный запуск ничего не пересчитывает: если готовый прогон профиля уже лежит на диске,
он просто читается. Чтобы пройти прогон заново, добавьте `--force` в скрипте или
поставьте `FORCE_RERUN = True` в ноутбуке.

Команды одинаковы в Linux, Colab, macOS и Windows PowerShell. На машине без GPU адаптер
выберет доступный backend, а конкретное устройство задаётся полем `runtime.device` в
YAML-конфиге. Прогон сохраняет промежуточные результаты по каждой трассе, поэтому
прерванный запуск продолжается с того же места.

Полный прогон в этой ветке ещё не выполнялся. В репозитории лежат результаты только
профиля `smoke2`.

## Что где лежит

| Путь | Содержимое |
|---|---|
| `notebooks/` | разбор датасета и разбор результатов прогона |
| `src/streamguard_bench/` | загрузка данных, адаптер guard-модели, движок replay, метрики и графики |
| `scripts/` | подготовка данных, запуск модели, сборка отчётов |
| `configs/` | закреплённые ревизии датасета и модели, список режимов и политик |
| `tests/` | тесты на контракт данных, движок, метрики и графики |
| `reports/tables/` | CSV-отчёты полного прогона |
| `data/` | кеш, подготовленный Parquet и результаты прогонов, всё вне Git |
| `docs/data_contract.md` | описание полей подготовленного датасета |

Каждый прогон сохраняет в `data/interim/qwen3guard/{профиль}/` решения по запросам и по
токенам ответа, результаты replay, список ошибок, список выбранных трасс и метаданные
запуска. Отчёты полного прогона попадают в `reports/tables/`, отчёты smoke-прогона
остаются рядом с его результатами, чтобы их нельзя было перепутать.



## История изменений

Прежний pipeline строил искусственный сбалансированный поднабор, приближал границу
опасного фрагмента интервалом и опирался на категории вреда. Его заменил полный набор из
210 трасс с точным onset, раздельными решениями по запросу и ответу и отдельными
отчётами по классификации и по потоку.
